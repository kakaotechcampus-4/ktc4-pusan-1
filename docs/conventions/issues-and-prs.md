# 이슈와 PR

기준 2026-11-10 · `develop` `c78c543`

## 이슈를 먼저 올립니다

브랜치 이름에 이슈 번호가 들어가고 PR 본문이 `Closes #` 로 시작하므로, 이슈가 없으면 그 둘을 채울 수 없습니다. 작업을 시작하기 전에 이슈를 올립니다.

템플릿은 `.github/ISSUE_TEMPLATE/` 에 두 개 있습니다.

### `feature.md` — 기능

```
작업 분야 → 작업 내용 → 상세 작업 → 완료 조건 → 참고
```

**완료 조건**이 이 템플릿의 핵심입니다. 여기가 비면 리뷰어가 「다 된 건지」를 판단할 기준이 없습니다. 「무엇이 되면 닫는다」를 확인 가능한 문장으로 적습니다.

### `bug.md` — 버그

```
발생 영역 → 버그 내용 → 재현 방법 → 기대 동작 → 실제 동작 → 환경 → 참고 자료
```

**재현 방법**을 번호 매긴 단계로 적습니다. 재현이 안 되면 고쳐졌는지도 확인할 수 없습니다. 환경은 Local / Dev / Prod 중 하나를 고릅니다.

## 1 이슈 = 1 PR

이슈 하나에 PR 하나입니다. 작업하다 다른 게 눈에 보이면 그 PR 에 끼워 넣지 않고 **새 이슈로 올립니다.** 승인이 1건만 필요한 구조에서 PR 이 커지면 리뷰어 한 명이 전부 떠안게 되고, 그러면 사실상 안 읽고 승인하는 쪽으로 갑니다.

## PR 본문

템플릿은 `.github/pull_request_template.md` 입니다. 지우지 말고 채웁니다.

| 칸 | 채우는 것 |
| --- | --- |
| 관련 Issue | `Closes #<번호>`. 이 줄이 있으면 머지될 때 이슈가 자동으로 닫힙니다. |
| 작업 내용 | 무엇을 왜 했는지. 이슈 본문 복사가 아니라, 실제로 선택한 것을 적습니다. |
| 주요 변경사항 | 파일·모듈 단위로. 리뷰어가 어디부터 볼지 정하는 자리입니다. |
| 테스트 | 체크박스 3개. **안 한 건 안 했다고 비워 둡니다.** |
| 화면/로그 | FE 는 스크린샷, BE·AI 는 로그나 응답 본문. |
| 리뷰 시 참고사항 | 봐 줬으면 하는 지점, 아직 못 정한 것, 일부러 남겨 둔 것. |
| Checklist | develop 최신 반영 / 불필요한 로그·주석 제거 / 환경변수·Secret 노출 없음 / 관련 Issue 연결. |

### 「리뷰 시 참고사항」을 빈 칸으로 두지 않습니다

리뷰어가 1명이라 어디를 봐야 하는지 알려 주지 않으면 그냥 승인하게 됩니다. 「여기는 아직 못 정했습니다」, 「이 숫자가 맞는지만 봐 주세요」 같은 한 줄이 리뷰 품질을 가장 많이 바꿉니다.

### 외부 도구 서명을 넣지 않습니다

PR 본문·이슈 본문·커밋 메시지에 생성 도구 이름, 세션 링크, `Co-Authored-By` 같은 자동 서명 줄을 남기지 않습니다. 공개 저장소이고, 저 줄이 「누가 이 판단을 했는지」를 흐립니다. 올리기 전에 본문을 한 번 읽고 지웁니다.

## 머지

승인 1건을 받으면 **PR 올린 사람이 직접 머지**합니다. merge commit 만 열려 있습니다. 머지 후에는 작업 브랜치를 지웁니다 — 지금은 안 지우고 쌓여 있어서, 이건 앞으로 맞추자는 쪽입니다.
