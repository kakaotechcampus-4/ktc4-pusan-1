# 리뷰

기준 2026-11-10 · `develop` `c78c543`

## 리뷰가 유일한 게이트입니다

`develop` 에는 필수 상태 검사가 없습니다. 승인 1건이면 CI 가 빨개도 머지 버튼이 열립니다. 즉 **CI 가 막아 주지 않는 것을 리뷰가 막습니다.** 리뷰어가 해야 하는 것 중에 「Checks 탭이 초록인지 본다」가 들어가는 이유입니다.

## 코멘트가 아니라 리뷰로 제출합니다

GitHub 에는 두 가지 길이 있고, 둘은 다릅니다.

| | 효과 |
| --- | --- |
| 하단 Conversation 코멘트 | 의견은 전달됩니다. 승인 수에는 **잡히지 않습니다.** |
| Files changed → Review changes → Approve / Request changes | 승인 1건으로 집계되어 머지가 열립니다. |

머지된 PR 들은 Approve 를 받고 들어왔습니다(예: #312). 다만 2026-11-10 기준으로 **열려 있던 PR 7건에는 Conversation 코멘트만 달려 있고 제출된 리뷰가 0건**이었습니다. 의견은 오갔는데 머지 버튼이 안 열리는 상태가 여기서 나옵니다. **승인할 마음이면 Approve 를 눌러야 합니다.**

## 리뷰어가 보는 것

이 순서는 지금까지의 리뷰를 규칙으로 굳힌 게 아니라 앞으로 이렇게 보자는 제안입니다. 위에서 걸리면 아래는 안 봐도 됩니다.

1. `Closes #` 가 있는지, 그 이슈의 **완료 조건이 실제로 충족됐는지**
2. Checks 탭 — 돌아야 할 CI 가 돌았는지, 초록인지
3. 변경 범위가 이슈 하나에 머물러 있는지. 끼워 넣은 게 있으면 빼 달라고 합니다
4. 환경 변수·토큰·키 값이 들어가 있지 않은지
5. 공개되는 산출물(발표 페이지, README 등)에 내부 메모나 작업 중 표시가 남아 있지 않은지
6. 그다음에 코드

## Request changes 를 쓰는 기준

고쳐야 할 게 있으면 Request changes 를 씁니다. 「일단 승인하고 나중에 고치자」는 승인 1건 구조에서 그냥 안 고쳐집니다.

쓸 때 같이 적습니다.

- 몇 번을 고쳐야 머지 가능한지 — **번호로** 적습니다
- 각 항목이 **차단인지 취향인지** 구분합니다. 취향은 `nit:` 을 붙입니다
- 작성자가 열어 둔 결정(「이거 뺄지 고민 중입니다」)에는 **결정을 돌려줍니다.** 리뷰어가 판단을 안 하면 PR 이 그 자리에 섭니다
- 마지막에 「무엇이 올라오면 승인하겠습니다」를 한 줄로 적습니다

## 작성자가 하는 것

- 지적마다 답을 남깁니다. 고쳤으면 커밋 링크를, 안 고치기로 했으면 이유를 적습니다
- 수정 푸시 후 **리뷰어에게 다시 리뷰를 요청**합니다(Reviewers 옆 ↻). 푸시만 하면 알림이 안 갑니다
- Request changes 는 리뷰어가 다시 승인해야 풀립니다. 자기 PR 을 자기가 승인할 수는 없습니다

## 말투

지시가 아니라 동료 말투로 씁니다. 「이거 왜 이렇게 했어요」 대신 「여기 이렇게 한 이유가 있나요, 없으면 ~쪽이 나을 것 같습니다」. 코드나 로그를 인용할 때는 원문을 그대로 붙입니다.

## 남겨 둔 것

- 리뷰 응답 기한을 정하지 않았습니다. 지금은 올린 사람이 채팅으로 부탁하는 식입니다.
- `assign-mentor.yml` 은 `base: main` 필터가 걸려 있어서 `develop → main` PR 에만 멘토를 붙입니다(`.github/workflows/assign-mentor.yml:19-21`). 내부 `feature/* → develop` PR 에는 run 자체가 생기지 않으므로, 내부 PR 의 승인 1건은 팀원이 채웁니다.
