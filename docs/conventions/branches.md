# 브랜치 전략

기준 2026-11-10 · `develop` `c78c543`

## 긴 브랜치 두 개

| 브랜치 | 역할 |
| --- | --- |
| `develop` | 기본 브랜치입니다. 모든 작업 브랜치가 여기로 들어오고, push 되면 `cd.yml` 이 배포합니다. |
| `main` | 주간 제출용입니다. `develop → main` PR 로만 올라갑니다. |

작업은 전부 `develop` 에서 따고 `develop` 으로 되돌립니다. `main` 에서 직접 브랜치를 따지 않습니다.

## 이름

```
<타입>/<이슈번호>-<영문-슬러그>
```

예: `feature/287-architecture-docs`, `fix/234-review-retry-cap`, `chore/103-fe-cd`

타입은 CI 가 인식하는 다섯 개를 씁니다 — `feature`, `fix`, `chore`, `refactor`, `perf`. 이 다섯 개는 `*-ci.yml` 의 `pull_request.branches` 에 그대로 적혀 있어서, 다른 접두어를 쓰면 **스택 PR 에서 CI 가 안 돕니다**(`.github/workflows/ai-ci.yml:9`).

슬러그는 영문 소문자와 하이픈으로 씁니다. 한글·대문자·공백은 쓰지 않습니다.

## 이슈 번호를 반드시 넣습니다

브랜치 이름의 이슈 번호가 「이 브랜치가 왜 있는지」를 유일하게 말해 주는 자리입니다. 지금 원격 작업 브랜치 54개 중 44개가 이 형태이고, 나머지 10개는 `feat/236` 처럼 슬러그가 없거나 `feature/ai-deepgram-stt` 처럼 이슈 번호가 없습니다. 과거 것을 고치지는 않고, **앞으로 올리는 것부터** 맞춥니다.

## 보호 규칙

`develop`(기본 브랜치)에 걸린 `dev protection` 이 전부입니다.

| 규칙 | 값 |
| --- | --- |
| PR 필수 | 예 |
| 필요한 승인 수 | **1** |
| 허용 머지 방식 | **merge commit 만** |
| 강제 푸시 | 금지 |
| 필수 상태 검사 | **`Lint, type check and test`(BE) · `Lint and build`(FE) · `Lint and test`(AI)** |
| CODEOWNERS 리뷰 필수 | 아니요 |

`main` 에는 삭제·강제푸시 금지만 걸려 있습니다. PR 필수가 아닙니다.

CI 가 빨가면 승인이 있어도 머지 버튼이 막힙니다.

세 검사는 PR 마다 **늘 돕니다**. 자기 영역(`backend/` · `frontend/` · `ai/`)을 안 건드린 PR 이면 첫 단계에서 바뀐 경로만 보고 나머지 단계를 건너뛰고 초록으로 끝납니다. 트리거에서 경로로 걸렀다면 검사가 아예 안 생겨 머지가 영영 막혔을 겁니다. 그래서 `be-ci.yml` · `fe-ci.yml` · `ai-ci.yml` 의 `pull_request` 에는 `paths` 를 다시 넣지 않습니다. 잡 `name` 을 바꾸면 필수 검사 이름도 같이 바꿔야 합니다.

저장소 관리자는 PR 에서 이 규칙을 건너뛸 수 있습니다. GitHub Actions 장애나 러너 이미지 변경처럼 코드와 상관없이 CI 가 깨져 급한 수정이 막힐 때를 위한 것이고, 평소에는 쓰지 않습니다.
