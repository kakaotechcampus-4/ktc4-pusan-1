# AI 분석 품질 지표와 측정 기록 (이슈 #318)

`ai` 파트의 평가 실행 기록은 `timeline-eval.md`(#48)와 `prep-eval.md`(#155)에 따로 쌓여
있습니다. 숫자는 다 있는데 **"무엇을 어떤 기준으로 셌는가"가 각 문서의 산문 안에 섞여
있어서**, 기본 모델을 `gpt-5.6-luna` → `gpt-6-luna` 로 바꾼 전후를 한눈에 비교할 수가
없었습니다. 이 문서는 지표의 정의와 측정 수단을 한자리에 모으고, **이미 기록된 실행만
다시 집계해서** before/after 표로 정리한 것입니다.

이 문서를 쓰면서 새로 호출한 모델은 없습니다. 아래 수치는 전부 위 두 문서에 적혀 있는
2026-09-13 / 10-07 / 10-16 실행에서 가져왔고, 비용 칸만 2026-11-10 콘솔에서 확인한 단가로
다시 계산했습니다. 단가와 확인일은 두 원 문서의 모델 표에 같은 문구로 적어 두었습니다.
`gpt-6-luna` 는 「2026-11-10 콘솔 확인」이고, `gpt-5.6-luna` 단가는 언제 확인한 값인지
기록이 없습니다 — before 쪽 비용 칸은 그만큼 불확실합니다.

## 1. 지금 저장소에 커밋되어 있는 측정 수단

| 수단 | 무엇을 재는가 | 어디에 있는가 | 돌리는 법 |
| --- | --- | --- | --- |
| 인용 접지 검사 | 모델이 만든 인용이 원문 발화의 부분 문자열인지 | 공통 함수는 `ai/src/irya_ai/pipeline/grounding.py` (`normalize` / `locate_quote` / `ground_finding`) | 각 단계 파이프라인 안에서 항상 돕니다. 따로 보려면 `uv run irya-ai ground <findings.json> <script.json> --strict` |
| Q&A 분절 골든 | 같은 대본에서 Q&A 쌍 수·질문 문장·답변 시작/끝이 그대로 나오는지 | 기대값 `ai/data/golden/qa_*.json` 2건, 검사 `ai/tests/test_qa_segmentation.py:193` | `uv run pytest tests/test_qa_segmentation.py` |
| 요약 표면 검사 | 핵심 사실 누락(`missing_key_facts`), 원문에 없는 숫자(`unsupported_numbers`) | `ai/src/irya_ai/evaluation.py` | `uv run pytest tests/test_evaluation.py` |
| LLM 실호출 기록 | 아래 2절의 지표 전부 | 기록은 `ai/docs/timeline-eval.md`, `ai/docs/prep-eval.md` | `uv run irya-ai timeline data/samples/chunks_backend_junior_01.json`, `uv run irya-ai prep data/samples/context_backend_junior.json` |
| 모델 없는 기준선 | 같은 입력을 추출 방식으로 돌린 결과 | `--backend extractive` | 위 두 명령에 `--backend extractive` |
| 단위 테스트 | 스키마·분절·폴러·STT·게이트웨이 응답 처리 | `ai/tests/test_*.py` 44개 파일, 최상위 `def test_` 함수 334개 (`parametrize` 때문에 실제 케이스 수는 더 많습니다) | `uv run pytest` |

접지 검사는 단계마다 쓰는 자리가 다릅니다.

- 타임라인은 `locate_quote` 로 후보 인용이 그 발화 안에 있는지 보고, 하나라도 어긋나면
  그 Q&A 초안을 통째로 버립니다 (`timeline.py:134`).
- 사전 가공은 `grounding.py` 의 `normalize` 만 가져다 쓰고, 인용이 이력서 원문에 있는지는
  자기 코드로 따로 봅니다 (`prep.py:235`). 인용 앞의 글머리 기호 하나는 떼고 비교하고
  ID 를 계산합니다 (`prep.py:121`). 「`- 10도`는 글머리, `-10도`는 온도」를 구분하려고
  마커 뒤 공백까지 봅니다.
- 면접 후 findings 는 `ground_finding` 을 그대로 써서 건별로 남기거나 버립니다
  (`findings.py:119`).
- CLI `ground` 는 `ground_findings` 로 kept / rejected 를 세어 출력합니다.

`tests/` 는 전부 HTTP mock 이라 키가 없어도 돕니다. 모델 호출이 필요한 것은 `irya-ai`
명령 쪽뿐이고, 그 결과는 사람이 문서에 적습니다 — 자동 채점기는 없습니다.

종료 코드는 세 명령이 같습니다: `completed` 0, `partial`·`failed` 1, 입력·설정 오류 2.
`ground --strict` 는 탈락이 하나라도 있으면 1 입니다.

### 1-1. 모델 없이 보장되는 것 — Q&A 분절 골든

Q&A 분절은 모델을 쓰지 않는 규칙 기반 단계라서, 유일하게 기대값을 파일로 박아 둘 수 있는
자리입니다. `ai/data/golden/qa_*.json` 두 건에 Q&A 쌍 12개(7 + 5)의 `sessionId`,
질문 문장 전문, `answerStartsWith`, 일부는 `answerEndsWith` 까지 적어 두었고,
`test_samples_match_golden` 이 같은 대본을 `--split-sentences` **켜고 끈 두 조건**으로
돌려 쌍 수·질문 문장·답변 시작/끝이 전부 일치하는지 봅니다
(`ai/tests/test_qa_segmentation.py:193`).

이게 보장하는 것은 다음 둘입니다.

- **문장 분리 옵션이 Q&A 경계를 흔들지 않습니다.** 발화를 문장 단위로 쪼개도 질문·답변의
  짝이 같습니다. 분절이 자막 청크 길이에 따라 달라지면 그 뒤 단계의 토큰 수와 인용
  대상이 다 같이 흔들리기 때문에, 여기부터 고정해 둔 것입니다.
- **같은 대본이면 같은 입력이 LLM 에 갑니다.** 위 before/after 비교에서 모델 쪽 차이만
  보려면 분절이 두 시점에 같아야 합니다. 골든은 2026-09-09 에 들어와 두 시점보다
  앞서고, `ai-ci.yml` 이 `uv run pytest` 를 돌리므로 그 사이 분절이 바뀌었다면 CI 가
  막았을 것입니다. 다만 당시 실행마다 이 검사를 따로 돌려 적어 둔 기록은 없습니다.

보장하지 않는 것도 분명합니다. 대본 2건은 사람이 만든 기대값이고, 답변 **본문 전체**가
아니라 시작·끝 문자열만 봅니다. 실제 STT 출력의 끊김·중복 발화는 이 골든에 없습니다.

## 2. 지표 정의

| 지표 | 정의 | 값의 출처 | 좋아지는 방향 |
| --- | --- | --- | --- |
| `status` | 산출물이 다 채워졌는지. `partial` 은 일부만, `failed` 은 못 만든 것 | 응답 JSON | `completed` |
| 선별 수 | 타임라인은 `moments / selected`, 사전 가공은 `역량 / 주장` 개수 | 응답 JSON | 타임라인은 입력 Q&A 수(샘플 7개)와 같아야 합니다. 사전 가공은 기대값을 정해 둔 게 없어서 회차 간 편차로만 봅니다 |
| 인용 수 | 모델이 붙인 인용의 총 개수 | 응답 JSON | 많다고 좋은 건 아닙니다. 회차 간 편차를 봅니다 |
| 탈락 수 | 단계가 거절한 산출물 수. 타임라인은 `rejectedMomentCount`, 사전 가공은 `rejections` 길이 | 응답 JSON | 0. 거절 사유는 인용 검증 실패만이 아니라 선택 밖 `qaId`·중복·빈 라벨·라벨 12자 초과·빈 answer·근거에 없는 숫자(`timeline.py:167-195`), 빈 이름·설명 길이·중복·상한 초과·인용할 이력서 원문 없음·인용이 이력서에 없음(`prep.py:166-247`)을 포함합니다 |
| 인용 접지 실패 사유 | `ground_finding` 이 돌려주는 세 가지 — 인용한 발화 자체가 없음, 인용이 그 발화에 없음, 다른 발화에는 있음 | `GroundingResult.reason` | 접지 검사는 NFC 정규화와 연속 공백 축약만 하고 **대소문자·띄어쓰기는 보정하지 않습니다**(`grounding.py:24-32`), 그래서 "비슷한 말"은 통과하지 못합니다 |
| 라벨 안정성 | 같은 입력 2회에서 글자까지 같은 라벨 수 / 전체 | 두 실행 결과를 사람이 대조 | 전체와 같아지는 쪽 |
| 인용 발화 ID 안정성 | 같은 입력 2회에서 같은 발화를 인용한 Q&A 수 / 전체 | 같음 | 같음 |
| 토큰 | `usage` 의 `prompt / completion / cached`. **`cached` 는 `prompt` 에 포함된 수**입니다 | 응답 `usage` | 낮은 쪽 |
| 추정 비용 | `(prompt - cached) × 입력단가 + cached × 캐시단가 + completion × 출력단가` | 위 토큰 + 콘솔 단가 | 낮은 쪽 |
| 소요 시간 | 명령 시작부터 응답까지 벽시계 | CLI 출력 | 낮은 쪽. 게이트웨이 혼잡이 섞입니다 |
| 문체 일관성 | `answer` 종결 어미가 실행 간에 같은지 | 결과 본문을 사람이 읽고 | 한 가지로 고정 |
| `answer` 길이 | 글자 수. `timeline-v2` 후보 상한은 120자 | 결과 본문 | 상한 안 |
| 골든 일치 | 같은 대본을 `--split-sentences` 켜고 끈 두 조건으로 분절했을 때 쌍 수·질문 문장·답변 시작·끝이 기대값과 같은 쌍 수 | `test_samples_match_golden` | 12쌍 전부 (지금 전부 통과) |

비용 식은 기록된 칸을 거꾸로 계산해서 맞춰 봤습니다. 예를 들어 타임라인 실행 2
(`gpt-5.6-luna`, prompt 1728 / cached 1725 / completion 1476)를 `cached ⊂ prompt` 로
계산하면 ₩2.75 가 나와 문서의 「약 ₩2.7」과 맞고, `cached` 를 별도 토큰으로 더하면
₩3.3 이 나와 맞지 않습니다. 캐시 단가는 입력의 1/10 입니다.

## 3. before / after — 기본 모델 교체

같은 코드·같은 입력이 아니라 **기본 모델을 바꾼 전후**를 비교한 것입니다. 두 시점이
같은 자리에서 측정된 게 아니라는 점은 원 문서에도 적혀 있습니다.

평균으로 봐도 결론이 달라지지 않기 때문입니다.

## 4. 무엇이 좋아졌고 무엇이 나빠졌는가

**좋아진 것**

- **비용이 1/2 밑으로 떨어졌습니다.** 타임라인 ₩3.0 → ₩1.3, ₩2.7 → ₩1.0. 사전 가공은
  3회 평균 ₩1.20 → ₩0.55 이고, 조건이 같은 before 실행 3 하나만 보면 ₩1.4 → 평균 ₩0.55
  입니다. 반올림 전 토큰으로 계산하면 각각 약 −57% / −65% / −54% 입니다.
  출력 단가가 ₩1,827 → ₩708 로 내려간 것이 대부분이고, 캐시된 입력이 ₩14 라 2회차부터는
  입력 비용이 거의 0 입니다.
- **문체가 고정됐습니다.** before 에서 실행 1·2 의 종결 어미가 갈렸던 것이, after 에서는
  `answer` 14개가 전부 「~했습니다」로 끝났습니다. 화면에 섞여 보이던 문제가 2회 관찰
  범위에서는 사라졌습니다.
- **사전 가공 소요가 줄었습니다.** 3회 평균 6.5s → 5.4s (약 −16%). before 실행 3 하나와
  비교하면 6.7s → 5.4s 입니다. 각 1회 측정이라 게이트웨이 혼잡이 섞입니다.
- **after 3회의 산출물 개수가 흔들리지 않습니다.** 역량·주장 수가 3회 모두 5 / 4 입니다.
  before 의 5~6 / 6~7 편차는 실행 2와 3 사이 수정이 섞여 있어 회차 간 흔들림이라고
  말할 수 없으므로, before 와 직접 비교하지 않습니다. 또 그 4 는 아래에 적은
  「두 줄이 빠진 4」라, 재현성이 올라간 것과 값이 맞는 것은 별개입니다.

**나빠진 것**

- **이력서 주장 2개를 놓칩니다.** 프롬프트가 같은 before 실행 3 은 주장 6개였는데,
  after 는 3회 모두 4개입니다. 빠진 둘은 기술 줄 주장 「Kubernetes 기반 배포 파이프라인
  구축」과 「GitHub Actions로 테스트와 배포를 자동화」입니다. before 에 넣은 「기술
  이름만 나열한 줄은 고르지 말라」를 기술 소제목 전체로 넓게 적용한 것으로 보이지만,
  **확인하지 않은 추측입니다.** 프로젝트 줄 주장 4개는 양쪽 모두 같습니다.
- **라벨 재현성이 내려갔습니다.** 2회 일치가 6/7 → 5/7 입니다. n=2 라 흔들림 범위 안일
  수 있습니다.

**after 에서 새로 본 것 (좋아짐·나빠짐으로 말할 수 없는 것)**

- **`answer` 길이가 상한을 넘습니다.** `qa_utt_020` 이 두 실행 모두 120자를 넘었습니다
  (127 / 138). before 에서는 글자 수를 재지 않아 비교 상대가 없습니다.
- **타임라인 인용 수가 21 → 18·20 입니다.** 탈락이 여전히 0 이라 틀린 인용이 늘어난 건
  아니고, 질문당 인용을 덜 붙인 것입니다. 많을수록 좋은 지표가 아니라 판단을 미룹니다.
- **타임라인 소요는 11.0~14.8s → 13.4~13.5s** 로 before 범위 안에 들어가, 변화라고 말할
  수 없습니다.

**안 변한 것**

- `status` 전부 `completed`, 타임라인 선별 7/7, 탈락 0. 두 시점 모두 같습니다.

## 5. 이 숫자를 읽을 때 주의할 것

- **n 이 작습니다.** 타임라인은 시점마다 2회, 사전 가공은 3회입니다. 「안정성」 칸은
  그만큼의 관찰입니다.
- **같은 시점 측정이 아닙니다.** before/after 사이에 코드도 같이 바뀌었습니다
  (`max_completion_tokens` 4,000 → 2,000 등). 사전 가공 프롬프트 변경은 before 3회
  안에서 일어났고, 그래서 위 비교는 before 실행 3 을 기준으로 잡았습니다. 차이를 모델
  교체 하나로 돌릴 수는 없습니다.
- **입력이 합성 샘플 한 건씩입니다.** 대본에서 만든 청크와 합성 이력서라 실제 STT 출력의
  띄어쓰기·대소문자 흔들림이 없습니다. 탈락이 계속 0 인 것은 입력이 깨끗하기 때문일 수
  있습니다.
- **소요 시간에 게이트웨이 혼잡이 섞입니다.** 각 1회 측정이고 같은 시각에 잰 게
  아닙니다.
- **비용은 추정입니다.** 콘솔 단가 × 응답 `usage` 이고, 청구서와 대조하지 않았습니다.
  추론 토큰은 `usage` 에 안 나와서 빠져 있습니다.
- **판정이 수동입니다.** 라벨·문체·인용 적절성은 사람이 결과를 읽고 적은 것이라 평가자
  한 명의 판단입니다. 기계가 판정하는 건 인용 접지 검사, Q&A 분절 골든, 요약 표면
  검사(`evaluation.py`) 셋뿐입니다.
