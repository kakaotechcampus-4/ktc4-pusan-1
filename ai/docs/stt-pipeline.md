# Elice STT 파이프라인

2026-09-13, [Issue #35](https://github.com/kakaotechcampus-4/ktc4-pusan-1/issues/35) / [PR #36](https://github.com/kakaotechcampus-4/ktc4-pusan-1/pull/36). PCM 입력을 청크별 전사와 `Utterance`로 바꾸는 AI 패키지다. LiveKit 오디오 구독, AI→BE→FE 전송, 녹화·재정렬, 제품 LLM Luna 연동은 포함하지 않는다. 아래 기본값은 구현 선택이며 팀 최종 합의나 실시간 성능 보장이 아니다.

## 입력과 청킹

- 입력은 little-endian PCM16 mono, 기본 16kHz다. WAV 파일 전체를 `push()`에 넣지 않는다. WAV 컨테이너는 요청 직전에 내부에서 만든다. 리샘플링·스테레오 변환은 호출자의 책임이다.
- 기본 20ms 프레임의 RMS로 음성 여부를 추정한다. 신경망 VAD가 아니며 낮은 음량·방 소음·실제 마이크에서 별도 검증이 필요하다.
- 700ms 침묵에서 구간을 나누며, 계속 말하면 버퍼 5초에 도달했을 때 마지막 1.5초의 가장 낮은 RMS 프레임을 찾아 자른다. 겹침은 없다.
- 보통 1초 미만 구간은 다음과 합친다. 종료 시에는 남은 짧은 음성도 보낸다. 음성으로 판정한 프레임이 없는 구간은 요청하지 않는다.
- `start_ms/end_ms`는 잘린 구간, `received_ms`는 그 경계를 결정할 때까지 처리한 오디오 위치다. 예를 들어 5초를 듣고 4초 지점에서 잘랐다면 결정 대기는 1초다. 앞당긴 경계가 그 대기를 없애지는 않는다.

## 호출 수명과 세션 정렬

`TranscriptionStream.push(pcm)`은 실행 중인 asyncio 루프에서 호출한다. 오디오 생산과 전사 소비를 함께 진행해야 한다. 입력이 열려 있고 큐가 비어 있으면 소비자는 다음 입력을 기다린다.

| API | 의미 |
| --- | --- |
| `push(pcm)` | 받아들인 청크 수 반환. 네트워크를 기다리지 않음 |
| `async for utterance in stream` | 해당 트랙의 소스 순서로 전달. 먼저 끝난 후속 요청도 선두를 기다림 |
| `close()` | 입력 종료, 꼬리 flush, 기존 작업은 계속 전달 |
| `drain()` | `close()`와 모든 작업 처리를 기다려 전체 결과 반환. close 없이 단독 호출하면 계속 대기 |
| `await aclose()` | 작업을 취소·회수하고 포기. 아직 전달하지 않은 결과는 나오지 않음 |

한 번에 소비자 하나만 진행한다. 소비자만 취소하면 요청은 남아 다음 소비자가 이어받을 수 있다. 완전히 떠날 때는 `aclose()`로 정리하고, HTTP 클라이언트도 소유자가 닫는다.

다중 트랙은 **세션당 하나의 `SessionOrdering`**을 공유한다. 각 트랙을 고정된 순서로 등록하고 실제 공통 시계의 `offset_ms`를 전달한다. ordering을 생략하면 단일 트랙용으로 간주하므로 두 화자에 각각 기본값을 쓰면 안 된다.

```python
from irya_ai.stt import SessionOrdering

ordering = SessionOrdering()  # 기본 capacity=16, 세션 동안 고정
interviewer_order = ordering.register("trk_interviewer", offset_ms=0)
candidate_order = ordering.register("trk_candidate", offset_ms=30_000)
# 각 TranscriptionStream(..., ordering=해당_order)에 전달한다.
# 예제 30초는 설명용이며 실제 참가 시각을 이 값으로 가정하지 않는다.
```

`seq = (offset_ms + track_start_ms) * capacity + ordinal`이며 **희소한 정렬 키**다. 개수나 연속 카운터로 쓰지 않는다. HTTP 완료 순서와 무관하게 두 화자의 Q&A 순서를 맞춘다. 이 매핑은 여러 트랙을 실시간 병합·전송하는 세션 서비스가 아니다.

하나의 스트림 객체는 하나의 연속된 오디오 수명을 가진다. 같은 트랙 ID로 새 객체를 만들면 샘플 시계와 청크 번호가 초기화되므로 재접속 복구로 사용할 수 없다. 공통 t=0·트랙 재접속·녹화 offset은 BE/FE/AI의 후속 계약이다. 현재 timestamp만으로 영상 seek 정확도를 보장하지 않는다.

현재 Elice 경로는 청크마다 `passType: FINAL`만 만들고 INTERIM·단어 목록을 만들지 않는다. 이것은 청크 응답 완료이며 `TranscriptSnapshot.stage: LIVE`는 계속 잠정본이다. 녹화 기반 REALIGNED 확정본을 생성하는 기능은 없다.

## 오류와 과부하

`EliceSttClient`는 multipart `file/model/language`를 보내고, 언어 기본값은 `korean`이다. 모델 기본값은 `whisper-large-v3`다. 키·배포 주소 설정은 [README](../README.md)를 따른다.

- 불량 JSON·타입·timestamp, 공급자 오류는 안전한 코드의 `SttError`로 처리한다. 실패한 청크를 기록하고 다음 정상 청크를 계속 전달한다.
- 401/403과 대부분의 4xx는 재시도하지 않는다. 일시적인 네트워크 오류·429·일부 상태·5xx는 제한된 재시도를 하며 요청 시간에는 이전 시도와 backoff가 포함된다.
- 패키지 오류 로그는 코드·청크 구간만 남긴다. 공급자 본문·전사·키·배포 주소를 복사하지 않으며, 생성 시 등록한 배포 호스트는 httpx/httpcore 메시지에서도 가린다. 다른 로거·임의 헤더의 비밀값까지 제거하는 기능은 아니다. 보호 범위와 수명은 [README의 로그 설명](../README.md#로그와-배포-주소)을 따른다.
- timestamp가 오디오 길이보다 500ms 넘는 응답을 거르는 것은 특정 오류 휴리스틱이다. 시간 안에 들어오는 오전사나 시간 정보 없는 응답의 환각까지 탐지하지 않는다.
- 기본 동시 요청 3개, 아직 소비하지 않은 작업은 최대 16개다. 초과 청크는 `OVERLOADED`로 기록하며 `dropped_spans`·`overloaded`로 조회한다. 요청 실패·빈 응답·timestamp 초과는 `rejected`, 취소는 timing outcome `ABANDONED`로 구분한다.
- 제한은 대기 PCM/태스크에 적용된다. timing·거절 메타데이터는 세션 길이에 따라 늘므로 보관·내보내기는 호출자가 관리한다. 큐 크기를 늘리면 전사가 더 오래 지연될 수 있다.
- 누락 음원의 재전송·녹화 복구는 없다. 통합 계층은 누락 구간을 분석 불완전성으로 전달해야 한다. 현재 분석기에 자동으로 이 상태를 전달하는 연결은 없으며 분석 `completed`가 전사 누락 없음을 증명하지 않는다.

## 지연의 정의

각 청크의 `timings`는 `ready_at → admitted_at → request_started_at → request_ended_at → released_at`을 단조 시계로 기록한다. 큐 대기, 요청, 선두 응답 대기와 전체 패키지 처리 시간을 따로 볼 수 있다.

`source_to_release_ms`는 오디오를 실시간 프레임 속도로 공급했다는 전제의 소스 시작→패키지 전달 계산값이다. 파일을 한꺼번에 넣거나 입력 자체가 지연되면 실제 발화 시각 측정으로 쓸 수 없다. 브라우저 수신·렌더, 후처리 LLM·전송 시간은 이 값에 없다. `proxy_display_lag_ms`는 기존 길이+요청시간 비교용 속성이며 화면 지연을 뜻하지 않는다.

화면의 무갱신 간격을 확인하려면 FE에서 연속 렌더 시각 차이를 별도로 기록해야 한다. 첫 샘플→표시 지연, 발화 끝→표시 지연, 화면 갱신 간격은 서로 다른 지표다. 5초 cap만으로 어느 지표의 상한도 보장하지 않는다.

## 기존 벤치마크와 공급자 관찰

6개 한국어 합성 TTS 파일의 최초 `72eb757` segmenter 경계와 별도 urllib HTTP 하네스 결과다. production 클라이언트·LiveKit·브라우저 측정이 아니다. 원본은 로컬 `stt-bench/`에 보존했고 Codex가 캐시를 독립 재계산했다.

| cap | 청크 수 | 전체 파일 Whisper 대비 문자 불일치율 | 문자열 항목 적중 | 과거 길이+요청 proxy p95 | 과거 요청 시간을 이용한 모의 재생 p95 |
| --- | --- | --- | --- | --- | --- |
| 5초 | 29 | 5.40% | 27/28 | 6.605초 | 6.876초 |
| 6초 | 26 | 4.35% | 27/28 | 7.464초 | 8.184초 |
| 7초 | 23 | 5.17% | 26/28 | 8.976초 | 9.436초 |
| 8초 | 23 | 3.32% | 28/28 | 9.498초 | 10.558초 |
| 10초 | 21 | 1.83% | 28/28 | 12.534초 | 13.114초 |

불일치율은 NFC·공백 제거 후 Levenshtein 거리의 6케이스 macro 평균이며 사람 정답 대비 CER이 아니다. 문자열 검사는 허용 표기를 둔 28항목이다. 5초 cap에서 조용한 지점 탐색을 끄면 8.93%, 25/28이었으나 27/28이 엄격한 상위집합은 아니다. 작은 TTS 표본이므로 사람 음성·환경 소음·동시 면접에 일반화하지 않는다.

표의 122청크는 해당 5개 설정만 센 수이며 전체 API 사용량이 아니다. 저장 응답에서 요청 실패·timestamp 초과는 0이었지만 일반적인 환각 부재를 뜻하지 않는다. 모의 재생은 과거 요청 시간을 재사용해 샘플 유입·동시성 3·순서 대기를 계산했고 신규 API 실측이 아니다. p95는 nearest rank다. 이번 적대적 리뷰의 추가 STT 호출은 0회다.

[Elice 공식 Whisper 문서](https://elice.io/en/ax/model-library/16ceb1c5-be5e-413f-8398-cfac8d8ce5d9)는 `return_timestamps="word"`를 설명한다. 반면 2026-09-12 확보된 사용 배포의 OpenAPI는 boolean/default true를 선언했고, 옵션을 생략한 캐시 470응답에서는 세그먼트 단위 span을 관찰했다. 명시적 `word` 값의 실제 수용·거부는 시험하지 않았다. 현재 무중첩 전략은 관찰된 세그먼트 타이밍을 근거로 유지하며, Elice 전체의 단어 시각 지원 불가나 모든 중복 제거 방법의 불가능성을 주장하지 않는다. warm-up 성공도 다음 요청의 지연을 보장하지 않는다.

## 다음 통합 테스트

자동 회귀와 독립 리뷰 결과는 [리뷰·검증 기록](stt-review.md)을 따른다. 후속 작업에서 아래를 실제 경로로 확인한다.

1. 두 화자의 실제 마이크·LiveKit 수신: 16kHz mono 변환, 한동안 침묵한 뒤 말하기, 30초 이상 연속 발화, 숫자·전문용어, 낮은 음량·소음.
2. 참가 시각 차이·교차 발화·응답 역전: 공통 시간과 seq, Q&A 답변 연결, 새 트랙/재접속 ID 정책.
3. 지연 계측: 샘플 캡처·청크 결정·큐·HTTP·전사 전달·후처리·FE 수신·렌더를 같은 trace로 연결하고 p50/p95 및 화면 무갱신 간격 기록.
4. 느린 공급자·인증/쿼터·타임아웃: 큐 상한과 누락 표시, STT·LLM 장애에도 통화 유지. 녹화가 구현된 뒤에만 녹화 유지까지 검증.
5. 사람이 교정한 소규모 정답 전사로 CER·숫자/부정 표현 보존 확인. 제품 LLM 연동 후 실제 전사→요약→인용의 품질·지연을 별도로 측정.
